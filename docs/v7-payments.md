## The payments switch, invoices and real-card testing

- **⚠️ Real payments are switched on PER ENVIRONMENT by `V7_PAYMENTS_ENABLED=true`** (read as `PAYMENTS_ENABLED` in `api/v7/payment/_hyp.js`; since 2026-09-29 — before that a hard-coded constant, off 2026-09-28). ON in Development (Roni is finishing payments in `vercel dev` against the **production** terminal), and **ON in Production since 2026-10-24** (set there with `HYP_ENV=production`, the `HYP_PROD_*` credentials and `V7_COUPONS_ENABLED=true`, after every earlier account was deleted; the portal's success URL points at `https://robin-music.com/api/v7/payment/return`). Being an env var, it can't be switched by deploying unrelated work. Wherever it's off: the payment step shows the OLD placeholder screen (`runPlaceholderPaymentStep` in `v7/result.js` — all fields optional, resolves with `''`), `GET /api/v7/payment/checkout` returns `{paymentsEnabled:false}`, POST returns 503, and signup requires no checkout (`paid_at` = signup time, as before Hyp). **Invoices** come from Hyp's own invoicing module (Hyp Invoice / EZcount: `SendHesh=True` → emailed to `email`), issued in the name of the business that owns the terminal — confirmed 2026-09-29 by the company's integration guide for another project. The module must be active on the terminal (on the test terminal it isn't — the portal shows "הרשמה למערכת החשבוניות" — which is why no test invoice ever arrived). That guide also copies every invoice to the company's bookkeeping inbox via `EZ.cc_emails` (not sent by us yet — the address comes from Dan). **Testing on the production terminal charges real cards** (the Hyp test card is declined there): each successful test is a real charge at the monthly price (₪200 — but in Development `V7_PRICE_OVERRIDE_ILS=2` makes it ₪2, and ₪1 for the first month with TEST50 while coupons are on) + a real standing order — cancel both (same-day `CancelTrans` before 22:00 IL costs no fee; the agreement via `scripts/_hyp-hk-status.mjs`).

## The Hyp payment step

- **Payment (Hyp, built 2026-09-27).** The payment step (`runPaymentStep` in `v7/result.js`) is Hyp Pay's hosted page (pay.hyp.co.il, formerly YaadPay — docs https://developers.hyp.co.il/pay; append `.md` to any page for raw Markdown, and use curl — WebFetch truncates the big reference pages) in an iframe. Product: **₪200/month, charged automatically by Hyp until cancelled** — a Hyp-managed recurring agreement (הוראת קבע: `HK=True&freq=1&Tash=999&OnlyOnApprove=True`); price is `MONTHLY_PRICE_ILS` in `api/v7/payment/_hyp.js` — but the **test terminal charges ₪10/month** (`TEST_TERMINAL_PRICE_ILS`, temporary, per Hyp's ~10 ILS test-amount advice; `monthlyPriceIls(env)` picks it). **Coupons** discount the FIRST month only (`TashFirstPayment`), percent-based, from `payment_coupons`. **Tax invoice** emailed by Hyp (`SendHesh=True`) — but only when Hyp's invoicing module is active on the terminal (see the ⚠️ bullet above; it is NOT on by default — the test terminal never sent one). The terminal's default document (portal → חשבוניות דיגיטליות → הגדרת מסמך ברירת מחדל) should be קבלה / חשבונית מס. No company number — the law requires one only above ₪5,000). No installments. Flow:
  0. **Everything is on ONE page** (since 2026-09-28): our billing form on top, Hyp's card form (iframe) right under it in a collapsible **"פרטי תשלום"** section (`.pay-toggle`, closed at first, opens by itself the first time the card form loads). Hyp needs the details inside the signed request, so the card form loads 0.7s after the name is typed (`NAME_SETTLE_MS`) and is **re-signed + reloaded on every detail change** (`change` event; a reload clears card digits already typed — owners fill top-down). Re-signs pass the page's `checkoutId`, and the endpoint updates that row while it's pending (same `Order`) instead of inserting; a failed/paid row gets a new one. **Coupons work since 2026-10-05 thanks to `FirstDate`** (see the end of this bullet); they're switched per environment by `V7_COUPONS_ENABLED` (see ENVIRONMENT VARIABLES; a code constant before 2026-09-29). The history: on the TEST terminal Hyp's server returned 500 after charging whenever a recurring page carried `TashFirstPayment` (every number format; the discounted first charge did go through) — reported to Hyp 2026-09-28, **reproduced on the production terminal 2026-09-29** (order 6: the ₪1 first charge went through and Hyp created the invoice, then crashed before emailing it or redirecting back). The exact request/response prepared for Hyp support is in `hyp-support/tashfirstpayment-request-response.json` (the folder is gitignored and local only — it holds emails + terminal numbers). A Chrome net-export of a failing production payment (order 8, 2026-09-29 09:33 UTC) showed the crash is inside Hyp: their own card form posts to `pay.hyp.co.il/cgi-bin/yaadpay/yaadpay.pl` and gets a bare 500 — the web server's stock "Internal Server Error" page (526 bytes, `comp@yaad.net`), i.e. their script crashed with no Hyp error code. To pull the payment requests out of such a log: `node scripts/_netlog-extract.mjs <netlog.json>` → `<log>.extract.txt`. **Fix from Hyp's tech rep (2026-10-05), verified the same day:** a `TashFirstPayment` page also needs **`FirstDate`** = the second charge's date, `YYYYMMDD`, one month after the first payment. It's missing from Hyp's docs. **Verified on the production terminal on 2026-10-05:** order 9 (TEST50, ₪1 first month, ₪2/month) came back through our return page, passed VERIFY, was marked paid and created standing order 543559. All four coupon attempts before it (orders 1, 2, 6, 8) were charged but never came back. (These notes said "not tested yet" until 2026-10-24.) `signPaymentPage` now sends it alongside `TashFirstPayment` only (`nextMonthIlDate`: today in Israel + 1 month, clamped to the month's last day), so full-price pages don't change. While off, the coupon field is hidden (the GET returns `couponsEnabled`) and any coupon is ignored. While on, the field checks the code inline (`GET /api/v7/payment/checkout?coupon=` → animated dots, then ✓ with the first-month price or ✗). Card-form loads (`sign` in `mountHypPayment`, `v7/hyp-payment.js`) run one at a time, so a burst of edits can't open a second checkout row. SIGN also sends `sendemail=True` (Hyp's payment confirmation, as in the company's working setup). **Hyp drops "+" from stored email addresses** (sent `roni.mark%2Btestb%40gmail.com`, stored `roni.marktestb@gmail.com` — a different, possibly stranger's, mailbox that the standing order would keep for every monthly invoice), so Hyp gets the account email **without its "+tag"** (`invoiceEmailFor` in `shared/invoice-email.js`, used by `_hyp.js` and shown on the payment screen as "החשבונית תישלח אל …"); the checkout row keeps the full address in `email` and the sent one in `billing.invoiceEmail`.
  1. The screen shows the price (`GET /api/v7/payment/checkout` → `{amountMonthly, couponsEnabled, env}`) + our own billing form: **שם מלא** (required — sent as `ClientName`, the cardholder), **כתובת** (optional → `street` + `EZ.customer_address`), **שם העסק** (optional — when filled the invoice is made out to it, via `EZ.customer_name`), **ח.פ / ע.מ** (optional, digits → `EZ.customer_crn`), and the coupon. Hyp's page uses **template 6 (`tmp=6`) — card fields only** (card, expiry, CVV, cardholder ID). `EZ.customer_name` / `EZ.customer_address` are NOT in Hyp's docs: they're fields of Hyp's invoicing service (Hyp Invoice, formerly EZcount) passed through like the documented `EZ.customer_crn` — confirm on a real test invoice. "המשך לתשלום" → `POST /api/v7/payment/checkout` validates billing (400 with a Hebrew message) and the coupon — **an unknown coupon never blocks the payment**: the page is signed at full price and the response carries `couponRejected: true` (the screen keeps its ✗ under the field) — inserts a pending `payment_checkouts` row (incl. `billing`), and signs the page with Hyp (`APISign`/`What=SIGN`; `Order` = the row's `order_no`). Amounts come only from the server and are covered by Hyp's signature.
  2. The iframe loads Hyp's page. On success Hyp redirects the iframe to the **"successful transaction" URL configured in each terminal's Hyp portal** (הגדרות → API-דף תשלום ו → הפנייה לאחר עסקה → עסקה שהצליחה → לינק מותאם אישית) = `<host>/api/v7/payment/return`. There is no per-request return URL, and **Hyp sends no server-to-server notification** — this redirect is the only signal.
  3. `api/v7/payment/return.js` forwards the raw query string, byte for byte, to Hyp's `What=VERIFY` (Hyp's Hebrew fields can be windows-1255 — never decode + re-encode), marks the row `paid` (storing `Id`, `HKId`, `ACode`, the raw query), and returns a tiny page that `postMessage`s the parent (same origin). The parent also polls `GET /api/v7/payment/status?id=` every 3s, so a lost message never strands the owner. Idempotent on reload.
  4. `runPaymentStep` resolves with the paid checkout id → `state.paidCheckoutId` → signup payload `checkoutId`. Signup **requires** a paid checkout (402 otherwise), claims it (`business_id`), and stamps `businesses.paid_at` from it; once claimed only the same email may reuse it (409) — the resend path re-posts it. Since 2026-10-25 a payment opens one account, ever: the database stamps `claimed_at` on the first claim and keeps it if the business is deleted, and signup refuses such a checkout (409). It also refuses a checkout paid on a different terminal than the deployment's (`hyp_env` ≠ `hypEnv()`, → 402), so a test-terminal payment can't open a production account. Internal test callers (`x-sonic-internal`) may omit `checkoutId`, so the walkthrough scripts still work.
  5. A paid-but-unclaimed checkout id is kept in localStorage (`rubin-v7-paid-checkout`), so going back or refreshing mid-funnel never charges twice; cleared after a successful signup.
  - **Terminals:** `HYP_ENV` = `test` (default) | `production` selects `HYP_TEST_*` or `HYP_PROD_*` (see ENVIRONMENT VARIABLES). Each checkout row records its `hyp_env` + `masof` and is verified against that terminal. Test card: `5253360311315452`, 12/29, CVV 493, ID 890108558. 3DS / Apple Pay / bit work only on production terminals. The portal toggle "אימות על ידי חתימה בעמודי התשלום" must be on (Hyp's docs put it under הגדרות → דף תשלום ו-API → אימות; it wasn't visible on the production terminal's menu on 2026-09-29 — if it's off, the card is charged but VERIFY fails and our page shows "התשלום לא אושר"). On the production terminal, the portal setting **"מניעת עסקאות כפולות"** may decline a repeat test with the same card and amount soon after the first.
  - **Same-origin requirement:** the return page is framed by our page, and `vercel.json` sets `X-Frame-Options: SAMEORIGIN` globally — the portal's return URL host must be the host the owner is on (robin-music.com vs sonic-brand.vercel.app matters in production).
  - **Credentials check:** `node scripts/_hyp-sign-probe.mjs` signs a page with the current terminal and prints its URL (CCode 902 = wrong PassP). Nothing is charged or written.
  - **Cancelling agreements by hand:** `node scripts/_hyp-hk-status.mjs <HKId> ...` terminates (`--resume` resumes) on the `HYP_ENV` terminal via `action=HKStatus`. Agreement numbers: `payment_checkouts.hyp_hk_id`, or the Hyp portal's standing-order list (which has no delete button). There's no API to list a terminal's agreements — never guess HKIds.
  - **Apple Pay / Google Pay: not possible (checked 2026-10-06).** They're switched on in the production terminal's portal, but Hyp drops both wallets from any page that carries a standing order. A wallet gives Hyp a single-use token, so it can't be charged again monthly. Three pages signed on the production terminal (no charge) confirmed it: both wallets show on one-time pages and are absent on our recurring page. Nothing to change in our code; if Hyp ever allows them on standing orders, Google Pay would appear by itself (the frame already has the permission), and Apple Pay would also need Hyp's one-time domain setup for framed pages.
  - **3DS (switched on in the production portal, 2026-10-06):** runs inside Hyp's page in our frame, so no code change. Portal advice given then: keep "חסום עסקאות שבוצעו בכרטיסי אשראי ישראכרט מקומי" unchecked (local Isracard cards don't support 3DS), leave "אילוץ אימות לקוח על ידי OTP" unchecked, and turn on the Fallback option. Not yet observed: whether the bank's code screen fits our 540px frame (make it taller if it's cut off), and whether the monthly standing-order charges skip 3DS (they normally do; Hyp's docs don't say).
  - **Refunds (researched 2026-10-13, not built):** Hyp Pay can refund through the API. Same day before 22:00 Israel time → `action=CancelTrans` (full amount, no fee; after 22:00 it returns `CCode=920`). Later → `action=zikoyAPI` with `Amount` (partial allowed, at most the original; `CCode=33` if more; returns a new `Id`; Hyp issues the refund document if its invoicing module is active). Both need the charge's `TransId`: we have it for first payments and renewals (`payment_checkouts.hyp_trans_id`), but not for the monthly standing-order charges, since Hyp sends no notice of them and Hyp Pay has no API that lists transactions (look them up in the portal). A refund doesn't stop the standing order; that's `HKStatus`. Doc pages and the full write-up: `hyp-support/hyp-refunds-guide.md` (written for Dan's project; local only).
  - **Not built yet:** visibility of later monthly charges (Hyp-managed charges send no notification — failures show only in the Hyp portal); refunds (see above). **No 100% coupon:** Hyp ignores a ₪0 first payment: with `TashFirstPayment=0.00` its page asks for the full monthly price, exactly like a page with no coupon (checked 2026-10-24 on the test terminal: ₪10/month page, first payment 0 → "הסכום לתשלום 10.00 ₪ חודשי"; first payment 5 → "5.00 ₪ מתוך 10.00 ₪"). So a 100% coupon would silently charge the full ₪200; coupons are capped at 99% (₪2 first month).

## Subscription section (Profile → מנוי)

- **Subscription section — Profile → "מנוי" (2026-10-06).** Shown only while `V7_PAYMENTS_ENABLED` is on AND the account has a paid checkout (`payment_checkouts.business_id`), so accounts that signed up while payments were off never see it. Endpoint `api/v7/account/subscription.js` (GET + POST cancel / resume); logic in `api/v7/account/_subscription.js`.
  - **Place and loading:** the Profile tab's sections run חשבון → opening hours → daily-playlist type → מנוי. The מנוי card is drawn at once, with a spinner inside until the data arrives, so it doesn't pop in a second late. It's hidden up front only when this browser remembers the account has none (localStorage `rubin-v7-sub-visible:<business id>`).
  - **Shows:** status, monthly price, next charge (date + amount), first payment date, the invoice email, and the invoice name + ח.פ.
  - **Not shown (Roni):** the first month's discounted price; the card (Hyp has no API to replace the card on an agreement, so there's nothing the owner could do with it); invoice downloads (they're in the owner's email).
  - **Charge dates are calculated, not reported.** Monthly on the first payment's Israel date, clamped to the month's last day (`nextChargeDate`). A charge day counts as already charged.
  - **Cancel** (two steps + an optional "למה אתם עוזבים?"): Hyp `HKStatus` NewStat=1 (`setAgreementStatus` in `_hyp.js`). Service runs to the end of the paid month: `businesses.subscription_ends_at` = midnight (Israel) at the next charge date. If Hyp's call fails, the cancellation is still recorded and the email says to terminate the agreement by hand in the portal.
  - **Resume:** only while cancelled and not yet ended (NewStat=2). Refused if Hyp's call fails.
  - **After the end:** the v7 cron skips the business (`subscription-ended`, silent), and `generate-daily`, `event-chat`, `save-event` and `event-playlist` return 402 `subscription_ended`. The Home tab shows `#subEndedBanner`.
  - **Renewal after the end (2026-10-06): a new payment, not the old standing order.** Hyp could resume a terminated agreement, but what it charges for the gap is undocumented. A new payment starts a new month today with a new agreement.
    - **Where:** Profile → מנוי shows "חידוש המנוי" (`#subRenew`) when ended; the Home banner and the "המנוי שלכם הסתיים" line link to it ("חדשו את המנוי").
    - **The form:** the onboarding payment screen, shared (`v7/hyp-payment.js` `mountHypPayment`), on a sheet (`#renewModal`, `startRenewal` in `v7/account/app.js`). Pre-filled with the last payment's details (`subscription.billing`). Coupons follow `V7_COUPONS_ENABLED`, like signup. The price is the current one.
    - **Server:** `POST /api/v7/payment/checkout` with `renewBusinessId` + the owner's JWT, allowed only once the subscription has ended (409 while active or still cancelled-not-ended — that's the free "resume"). The checkout row is tied to the business from the start (`business_id`), with the account's email.
    - **Reactivation happens on Hyp's confirmation:** `return.js` calls `renewSubscription` (`_subscription.js`) BEFORE marking the row paid. It clears the three cancellation columns, audits `subscription` (`renewed: true`) and emails ronnie@ "חידוש מנוי". So a tab closed right after paying still comes back. If the subscription is already active (paid twice), nothing changes and the email says to cancel the extra standing order and refund it. If reactivation fails, the row is still marked paid and the email asks for a manual fix.
    - **After paying:** the section's dates restart from the renewal (the view reads the newest paid checkout). The page builds today's playlists right away if the place is open today and nothing was built yet (reason `before-build` / `error`), like the first login.
  - **Emails to ronnie@algorithm-media.com** (`OPS_EMAIL_TO` + `emailOps` in `api/v7/_ops-email.js`; subject prefixed "[בדיקה]" outside Vercel production):
    - **every new subscription:** `signup.js` sends it when it claims a paid checkout (once — a resend finds it already claimed). Signups without a payment (payments off) send nothing.
    - **every cancel / resume**, which is also audited in `business_settings_changes` (field `subscription`).
  - **Needs migration** [`v5/precompute/migrations/2026-10-06-v7-subscription-cancel.sql`](../v5/precompute/migrations/2026-10-06-v7-subscription-cancel.sql). Without it the section answers 501 and stays hidden, and nothing counts as ended.
  - Tests: `node --test scripts/test-subscription-dates.mjs`.
